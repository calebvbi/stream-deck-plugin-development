# Getting Started and Project Structure

Verified against current Elgato documentation on 2026-08-26.

## Current development prerequisites

For new plugin development, Elgato currently documents:

- Node.js 24 or higher.
- Stream Deck 7.1 or higher.
- A Stream Deck device (Stream Deck Mobile can be used if physical hardware is unavailable).
- A terminal and editor.
- Stream Deck CLI (`@elgato/cli`).

Recommended Node setup uses a version manager such as `nvm` or `nvm-windows`.

```bash
nvm install 24
nvm use 24
node -v
```

Inspect the existing CLI and current published version before changing the global toolchain:

```bash
streamdeck -v
npm view @elgato/cli version
```

If installation or an update is required, record the resolved version and obtain
authorization before running `npm install -g @elgato/cli@<resolved-version>`.

## Decide before scaffolding

Record these choices before `streamdeck create`:

- Keypad, Encoder, and/or Neo controller surfaces.
- Property inspector needs and action-versus-global settings scope.
- External app, service, device, or self-contained behavior and its authentication boundary.
- Stream Deck, Node.js, and operating-system compatibility floors.
- Local-only, direct distribution, or Marketplace release intent and resulting asset/support needs.
- Scaffold destination, author identity, name, description, and permanent reverse-DNS UUID.

## Scaffold a plugin

```bash
streamdeck create
```

The wizard asks for author, plugin name, UUID, and description. It writes a new
directory below the current working directory, enables developer mode, installs
dependencies, builds, and installs the generated plugin. Confirm the destination and
these side effects before running it in an agent workflow.

## Standard generated structure

```text
.
├── <plugin-uuid>.sdPlugin/
│   ├── bin/
│   ├── imgs/
│   ├── logs/
│   ├── ui/
│   └── manifest.json
├── src/
│   ├── actions/
│   └── plugin.ts (or the entry file generated by the current scaffold)
├── package.json
├── rollup.config.mjs
└── tsconfig.json
```

Important distinction:

- `*.sdPlugin/bin/` is compiled output.
- `manifest.json`, `ui/`, images, layouts, localization files, and other authored assets inside `*.sdPlugin/` are project inputs/resources, not disposable generated code.

Do not manually edit compiled files in `bin/`.

## Standard scripts

Current Elgato scaffolding provides a one-shot build and a watch mode:

```bash
npm run build
npm run watch
```

The standard `watch` script watches source/manifest changes and restarts the plugin after rebuilding. Use it for interactive development.

For agent validation, prefer the one-shot build unless a long-running watcher is explicitly useful.

## Runtime model

A Stream Deck plugin has two JavaScript environments:

- Application layer: Node.js plugin backend.
- Property inspector: Chromium-based HTML frontend inside Stream Deck.

Current Stream Deck 7.1+ supports Node.js 20 and 24 runtimes, while current plugin-development guidance uses Node.js 24+.

Do not assume Node/browser APIs are interchangeable between the backend and property inspector.

## Compatibility principle

For existing repositories, preserve the currently declared versions unless the requested feature requires raising them. Newer development prerequisites do not automatically mean an existing plugin must drop older supported Stream Deck versions.

An unchanged manifest is not compatibility proof. For every new SDK method, event,
manifest field, controller surface, Chromium feature, or Node.js feature:

1. Lock the current manifest, package lock, and declared minimum host/OS versions.
2. Check the live schema, Stream Deck changelog, plugin-environment runtime table, and
   applicable SDK migration notes for the feature's introduction and breaking changes.
3. Compile against the repository's installed dependency, then package and run the
   exact artifact on the declared minimum Stream Deck and OS versions.
4. If the feature is unavailable at that floor, implement an approved fallback or
   obtain approval to raise the requirement; do not silently change compatibility.
5. Keep current-host results separate from minimum-host evidence.
